**Points clés**

- Exemple cURL `POST /api/trading/quotes` avec `X-Auth-Client`, `X-Auth-Timestamp: $(date +%s)`, `X-Auth-Nonce: $(uuidgen)`, `X-Auth-Signature`, corps `base_currency`, `quote_currency`, `side: "buy"`, `quantity: "0.0001"`.

- Ressources : API reference, Open API (Swagger), Postman.

### 3.2 SDK Installation
Lien : https://bitnob.dev/docs/developer-resources/_sdks

**À quoi ça sert** : installation des SDK officiels. Page à préfixe `_` (probablement non publiée/obsolète).

**Points clés**
- Node.js/TS : `npm install @bitnob/node-sdk` ; `new Bitnob({ clientId, secretKey, environment: 'sandbox' | 'production' })` ; `bitnob.wallets.getBalances()`.
- Python : `pip install bitnob` ; `Bitnob(client_id, secret_key, environment)` ; `client.wallets.get_balances()`.
- Go : `go get github.com/bitnob/bitnob-go` ; `bitnob.NewClient(WithClientID, WithSecretKey, WithEnvironment(bitnob.Sandbox))`.
- PHP : `composer require bitnob/bitnob-php`.
- Direct API (cURL) : base `https://api.bitnob.com/api/balances`.

**Pièges (contradiction de signature)** : l'exemple cURL calcule `SIGNING_STRING="${CLIENT_ID}GET/api/balances${TIMESTAMP}"`, timestamp en **millisecondes** (`date +%s%3N`), nonce `uuidgen`, signature en **base64**. Cela contredit la doc d'auth (`CLIENT_ID:TIMESTAMP:NONCE:PAYLOAD`, secondes, nonce hex 16 octets, signature **hex**, voir `genesis.md` §2.5). Ne pas utiliser cet exemple. Existence réelle de ces SDK : non vérifiable ici (Home dit « Coming soon »).

### 3.3 Postman Collection
Lien : https://bitnob.dev/docs/developer-resources/postman-collection

**À quoi ça sert** : collection Postman de l'API v2 avec signature HMAC automatique.

**Points clés**
- Variables d'environnement : `base_url` (`https://api.bitnob.com`, la même en sandbox et prod), `client_id`, `client_secret`, `quote_id`, `upload_id`.
- Le script de pré-requête génère `timestamp` + `nonce`, canonicalise le corps JSON, calcule `HmacSHA256(client_id:timestamp:nonce:body, client_secret)` et injecte `X-Auth-Client`, `X-Auth-Timestamp`, `X-Auth-Nonce`, `X-Auth-Signature`.
- Le mode (sandbox/prod) est déterminé par le `client_secret`, pas par l'URL ; `client_id` partagé.
- Couverture : Identity (`GET /api/whoami`), Balances, Addresses, Transactions, Withdrawals, Exchange rates, Trading (market, scheduled, target : DCA + take-profit), Bulk transfers (CSV/XLSX, récurrence), Payouts, Virtual accounts (+ simulateur de dépôt sandbox), Cards, Lightning (invoices, payments, node operations), Customers (KYC), Beneficiaries.
- Erreurs au format **RFC 7807** : `type`, `title`, `status`, `detail`, `correlation_id`, `timestamp`.
- Dépannage 401 : vérifier `client_id`/`client_secret` non inversés ; absence de `X-Auth-Signature` = script non exécuté ; après rotation, l'ancienne paire est invalide immédiatement.
- Webhook testing : exemples de vérification de signature, validation de payload, gestion d'événements, simulation de retries.
- Support : https://support.bitnob.com.

### 3.4 Swagger API Explorer
Lien : https://bitnob.dev/docs/developer-resources/swagger-explorer

**À quoi ça sert** : télécharger la spec OpenAPI 3.0 de l'API v2 (`bitnob-api-v2.openapi.json` / `.yaml`, servies sous `/api-collections/swagger/`).

**Points clés**
- `info.version` = `2.0.0`. Le schéma de sécurité documente les 4 en-têtes HMAC ; erreurs via schéma `Problem` (`correlation_id`, `detail`).
- Couverture annoncée « 100 % » : Identity `GET /api/whoami`, Balances, Addresses, Transactions, Withdrawals, Exchange rates, Trading (orders market/scheduled/target), Bulk transfers, Payouts, Virtual accounts, Cards (terminate = le seul `DELETE` de la v2), **Lightning (Invoices, payments, node operations : `/api-reference/lightning#create-invoice`, `#initiate-payment`)**, Customers, Beneficiaries.
- Workflow : générer un client avec `openapi-generator-cli`, valider sur sandbox via `GET /api/whoami`, basculer en prod en changeant seulement le `client_secret` (même `client_id`, même `base_url`).
- Sécurité d'environnement : mélanger les secrets renvoie **401**.
- Outils suggérés : Schemathesis, Spectral, Prism, oasdiff.

### 3.5 Wallet Infrastructure API
Lien : https://bitnob.dev/docs/developer-resources/wallet-infrastructure-api

**À quoi ça sert** : Postman + OpenAPI de l'API Enterprise (Wallet-as-a-Service).

**Points clés**
- Auth : `X-API-Key` (pas de HMAC), base `https://api.platform.bitnob.com`, `GET /me` pour tester (Get API Key Info).

## 4. Enterprise

### 4.1 Enterprise Overview
Liens : https://bitnob.dev/docs/enterprise et https://bitnob.dev/docs/enterprise/overview (identiques)

**À quoi ça sert** : présente l'API Enterprise (wallet-as-a-service multi-chaînes, gouvernée par politiques) pour banques, exchanges, fintechs. Hors périmètre d'un simple encaissement Lightning.

**Points clés**
- Fonctions : wallets/adresses illimités sur 10+ chaînes via vaults HD (BIP-39), moteur de politiques (limites, whitelists, plafonds de vélocité, approbations multi-parties), gas stations (dont Tron energy/bandwidth), batch jusqu'à **100 transferts** par appel, abonnements/webhooks sur dépôts, exports et analytics. Latence de signature 50-100 ms ; « no volume caps ».
- Sécurité : Bitnob Secure Enclave sur AWS Nitro Enclaves ; Bitnob ne peut pas déplacer les fonds unilatéralement ; root quorum ; audit logs immuables ; quotas RPC par jour ; clés d'idempotence sur toutes les mutations.
- Chaînes (identifiant / natif / réseaux) : ethereum / ETH / mainnet, sepolia ; bitcoin / BTC / mainnet, testnet ; solana / SOL / mainnet-beta, devnet ; tron / TRX / mainnet, shasta ; polygon / POL / mainnet, amoy ; base / ETH / mainnet, sepolia ; arbitrum / ETH / one, sepolia ; bsc / BNB / mainnet, testnet ; optimism / ETH / mainnet, sepolia ; avalanche / AVAX / mainnet, fuji. Liste vivante : `List Chains`.
- Lightning : **non listé** dans les chaînes Enterprise.

### 4.2 Authentication (Enterprise)
Lien : https://bitnob.dev/docs/enterprise/authentication

**Points clés**
- Base `https://api.platform.bitnob.com`. En-têtes : `X-API-Key` (oui), `X-API-VERSION` (non, défaut `v1`), `Content-Type: application/json` (écritures POST/PUT/PATCH).
- Organisation déduite de la clé ; aucune clé côté mobile/front.
- Autorisation : jamais de challenge WebAuthn/MFA pour une clé API. Flux : (1) clé vérifiée (active + permission), (2) politiques évaluées, (3) Enclave signe ou met en attente (`require_approval` -> `pending_authorization`), (4) broadcast (avec top-up de gas si besoin).
- Versioning : en-tête `X-API-VERSION: v1` (recommandé) ou préfixe de chemin `/v1/wallets`.
- **Idempotence** : `idempotency_key` obligatoire dans le corps pour créer vaults, wallets, transactions ; chaîne de **1 à 64 caractères** ; même clé rejouée après succès = résultat original sans ré-exécution ; requête encore en cours = **409 Conflict**.

### 4.3 Core Concepts (Enterprise)
Lien : https://bitnob.dev/docs/enterprise/core-concepts

**Points clés**
- Hiérarchie : Organisation > Vault (HD) > Wallet (par chaîne) > Address. Vault `dedicated` (1 wallet/chaîne) ou `pool` (illimité) ; le choix est irréversible.
- Types de wallet : `hot`, `cold` (seuils d'approbation élevés), `operational`.
- Politiques : actions `block`, `alert`, `require_approval`, `delay` ; catégories `access`, `whitelist`, `limits`, `approvals`, `velocity`, `compliance`, `quorum` ; première règle correspondante gagne ; root quorum à configurer avant la prod.
- Gas stations par chaîne/réseau, `auto_refill_enabled`, `refill_from_wallet_id`, `GET /gasstations/stats`, transaction liée `gas_sponsorship` via `sponsor_tx_id`.
- Address book immuable ; validée contre la chaîne.
- Statuts de transaction : `pending_signature`, `pending_authorization`, `signed`, `awaiting_sponsorship`, `broadcasting`, `confirming`, `completed` (terminal), `failed` (terminal), `cancelled` (terminal), `rejected` (terminal).

### 4.4 Exchange Integration Guide
Lien : https://bitnob.dev/docs/enterprise/exchange-integration-guide

**À quoi ça sert** : tutoriel en 8 étapes pour un exchange (hors besoin direct DioteKo).

**Routes citées** : `POST /vaults` (`vault_type: "pool"`, `idempotency_key`) ; `POST /vaults/:vault_id/wallets` (`chain`, `customer_ref_id`, `wallet_type`, `asset_ids`, `network`, `idempotency_key`) ; `GET /transactions?wallet_id&direction=inbound&status=completed&period=24h` ; `POST /gasstations` ; `POST /gasstations/:id/stake` (`amount`, `resource: "ENERGY"`) ; `POST /transactions` (`wallet_id`, `to_address`, `amount`, `asset_id`, `network`, `fee_level`, `sponsor_gas`, `idempotency_key`) ; `POST /policies/quorum`, `POST /policies` (priorités plus hautes évaluées en premier : 300 whitelist, 200 limites, 150 vélocité) ; `POST /addressbook` ; `GET /gasstations/stats`, `GET /policies/stats`, `GET /transactions/analytics`, `GET /transactions/export?...&format=csv`.
- Détection des dépôts : polling ou abonnements (`incoming_token_tx`, `confirmation_threshold_met`) ; créditer seulement à `completed` avec confirmations suffisantes, réconcilier `amount_decimal` et `asset_symbol`.
- Réconciliation quotidienne : rapprocher `idempotency_key`, alerter si bloqué en `pending_authorization`, rafraîchir les gas stations avant `health_status` = low, `Retry Delivery Event`.

### 8.2 Mastering Bitcoin Core from the Command Line (cours)
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line

Cours pratique (mis à jour 05/2025, anglais) sur `bitcoind`, `bitcoin-cli` et `regtest`. 8 modules, « 1h 25m total length ». Objectifs : nœud local, regtest, wallets/adresses (Bech32, legacy), transactions brutes, inspection de la chaîne/mempool, scripts Bash/Python. Capstone : outil CLI qui démarre regtest, mine 101 blocs, crée un wallet, envoie à deux adresses, confirme, affiche hex et JSON décodé. Quiz final annoncé « 15-20 questions + 3 scénarios » (mais la page du quiz dit 25 questions, voir §8.13).

### 8.3 Module 1 : Installing & Running Bitcoin Core
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/module-1
Bitcoin Core = implémentation de référence (`bitcoind` démon, `bitcoin-cli` client). Prérequis : Linux/macOS, 2-4 Go RAM, ~500 Mo regtest vs ~500 Go+ mainnet. Installation de la version 25.0, `bitcoind -regtest -daemon`, `bitcoin-cli -regtest getblockchaininfo` (chain regtest, blocks 0), `bitcoin.conf` (`regtest=1 server=1 daemon=1 rpcuser rpcpassword fallbackfee=0.0001`), arrêt via `stop`. Activité : créer un wallet, `getnewaddress`, `generatetoaddress 101` (adresse retirée du texte), `getbalance`.

### 8.4 Module 2 : Bitcoin Core Architecture
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/module-2
Full node (valide tout, ~800 Go mainnet) ; `bitcoind` serveur vs `bitcoin-cli` simple frontend. Répertoire de données (`blocks/`, `chainstate/`, `wallets/`, `mempool.dat`, `debug.log`, `bitcoin.conf`), mempool (`getrawmempool`), mode multi-wallet. Ports RPC : mainnet 8332, testnet 18332, regtest 18443 ; auth par cookie ou `rpcuser/rpcpassword` ; ne jamais exposer le RPC publiquement.

### 8.5 Module 3 : Wallets and Addresses in Bitcoin Core
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/module-3
`createwallet`, `loadwallet`, `listwallets`, `getnewaddress [label] [type]`. Formats : Bech32 (`bc1…`, `bech32`), P2SH-SegWit (`3…`, `p2sh-segwit`), legacy (`1…`, `legacy`) ; privilégier Bech32. Wallets actifs vs watch-only (`importaddress`). Labels (`getaddressesbylabel`, `listreceivedbylabel`) pour suivre clients/flux.

### 8.6 Module 4 : Using Regtest to Simulate Bitcoin
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/module-4
Regtest : réseau privé hors ligne, blocs instantanés, confirmation immédiate. `generatetoaddress 101` pour débloquer les coinbase (maturité), `sendtoaddress`, `getrawmempool`, `generatetoaddress 1` pour confirmer. Alternative GUI : Polar (Bitcoin Core + LND + Core Lightning via Docker).

### 8.7 Module 5 : Transactions and UTXO Control
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/module-5
Modèle UTXO ; `listunspent`, `createrawtransaction`, `signrawtransactionwithwallet`, `sendrawtransaction`, `gettransaction`, `decoderawtransaction` (vin/vout, types de script). Les blocs de code sont vides dans le corps de la page et repris en fin de page.

### 8.8 Module 6 : Blocks and Blockchain State
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/module-6
`getbestblockhash`, `getblock`, `getblockheader`, `getblockhash`, `getchaintips`, `invalidateblock` pour simuler une réorganisation, confirmations = nombre de blocs au-dessus, `getrawtransaction … true`, `getmempoolentry`.

### 8.9 Module 7 : Working with Bitcoin RPC
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/module-7
JSON-RPC via `curl` (`"jsonrpc":"1.0"`, `id`, `method`, `params`, port 18443 en regtest), auth cookie (`~/.bitcoin/regtest/.cookie`) ou user/password, sécurisation (`rpcbind=127.0.0.1`, `rpcallowip`, tunnel SSH, rotation du mot de passe).

### 8.10 Module 8 : Developing with Bitcoin Core Locally
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/module-8
Environnements de test regtest, scripts Bash/Python (requests + HTTPBasicAuth), simulation de confirmations et de réorgs, notes de production : nœud élagué (`prune=550`, ~1 Go vs 500 Go+), séparer service wallet et nœud (`disablewallet=1` sur le nœud public, flux de dépôt/retrait avec `createrawtransaction` / `signrawtransactionwithwallet` / `sendrawtransaction`).

### 8.11 Capstone Project : Bitcoin Core CLI Automation
Lien : https://bitnob.dev/docs/courses/mastering-bitcoin-core-from-the-command-line/Capstone-Project-Bitcoin-Core-CLI-Automation
Spécification : démarrer regtest, créer le wallet `capstone`, miner 101 blocs, envoyer 0.25 BTC à deux adresses via `sendmany`, miner 1 bloc, afficher `getrawtransaction` + `decoderawtransaction`. Critères : une seule commande, soldes avant/après, hex complet, JSON décodé, gestion d'erreurs (wallet existant), fichier de log horodaté, réinitialisation de la chaîne regtest.

## À retenir pour DioteKo

### Encaissement Lightning (factures, preimage, statuts)
- Le lot confirme que la **Lightning API existe** (« Invoices, payments, and node operations ») avec les ancres `/api-reference/lightning#create-invoice` et `#initiate-payment` (swagger-explorer, postman-collection), mais **ne détaille ni création de facture, ni statuts, ni webhook de réception**. Ces détails sont hors lot et à vérifier dans l'API reference.
- Aucun changelog ne traite de Lightning ; les webhooks stablecoin `transfer.success` / `deposit.success` / `transfer.failed` sont les seuls événements « transfer » documentés (changelog 2026-06-12).

### Webhooks (noms d'événements, signature, retries)
- Payouts : `payouts.initialized`, `payouts.processing`, `payouts.withdrawal.success`, `payouts.withdrawal.expired` ; ne pas se baser sur `data.status` mais sur `event` ; ancien format `payout.transfer.*` remplacé (changelog 2026-07-20, home).
- Signature API standard : `x-bitnob-signature`, HMAC **SHA512** (changelog 2026-06-12). Enterprise : HMAC-SHA256 sur `{data, event, timestamp}` (wallet-infrastructure-api).
- IP sources : `18.171.51.218`, `13.134.154.133` (changelog 2026-07-23).
- `event_id` de premier niveau pour dédupliquer ; `transfer.success` contient `transaction_id` (changelog 2026-05-15).

### Sandbox vs live, clés, go-live
- Base URL unique `https://api.bitnob.com`, `client_id` commun, **secret différent** ; secrets mélangés -> 401 (swagger-explorer, postman-collection).
- `GET /api/whoami` pour le smoke test ; Playground « Try it out » signe vraiment les requêtes (changelog 2026-07-15) : attention à ne pas l'utiliser avec un secret de prod par erreur.
- Virtual Accounts : un `simulate-deposit` sandbox existe sous `/api/virtual-accounts` (chemin exact non précisé dans ces pages ; lien `/api-reference/virtual-accounts#simulate-deposit`), valable pour les virtual accounts uniquement.

### Idempotence (`reference`)
- API standard : `reference` ; Virtual Accounts : « `reference` acts as the idempotency key » (changelog 2026-08-09). Enterprise : `idempotency_key` 1-64 caractères + 409 en vol (enterprise/authentication).

### Unités de montants
- Cartes : micro-unités entières (1 USD = 1 000 000) + `displayAmount` (changelog 2026-05-19). Autres webhooks : non précisé. Les balances sont en plus petites unités (voir `genesis.md`).

### Limites / KYC
- Retrait stablecoin : minimum **10 USD** depuis le 2026-08-21 (Breaking). Card KYC activé par compte ; Virtual Accounts exigent BVN ; NGN activé par compte.
- Enterprise : lots de 100 transferts max, pas de plafond de volume (hors politiques).
