# Plan — agent de scraping (Playwright) + module KYC Idswyft

## Context
Deux demandes de l'utilisateur :
1. **Un agent dédié au scraping** qui utilise la skill `/playwright` (Chromium headless) pour lire leurs sites, leurs instances Docker (ex. `http://localhost:8086`, `:8000/api/docs`) ou des sites tiers, et qui soit déclaré dans `CLAUDE.md` et les docs `.claude/`.
2. **Un flux KYC avec Idswyft**, en s'appuyant sur l'instance **déjà installée et lancée** dans `C:\ProjetGit2\db\KYC-Module` (`docker-compose-idswyft.yml`, `docker-compose.kyc-kyb.yml`).
   **Portée décidée (précisée par l'utilisateur) :** on **se concentre sur la résidence** (et l'identité) : KYC **appliqué** dès maintenant. Naissance, mariage et décès ne sont « optionnels » que **provisoirement** : au fond ils sont **obligatoires** (surtout la naissance, dont les données sont celles du titulaire ; le nom du père ou de la mère peut poser problème et devra être complété). Le code doit donc **laisser une brèche ouverte** : une politique KYC par type (`required` / `planned`) où `planned` = cible obligatoire, non bloquant aujourd'hui, activable en changeant une valeur, sans refaire le module.

Faits vérifiés (lecture de l'instance via la skill) : Idswyft v1.12.19, API `http://localhost:8000` (`/api/docs`, `/api/health`), dashboard `http://localhost:8086` (connexion OTP, le code se lit dans `docker logs idswyft_api`), clés API créées depuis le dashboard (`X-API-Key`). Flux documenté : `POST /api/v2/verify/initialize` → `…/:id/front-document` → `…/back-document` → `…/live-capture` → `GET …/status` (`verified | failed | manual_review`) ; webhooks `POST /api/webhooks/register` ; révision manuelle côté Idswyft `PUT /api/admin/verification/:id/review`. Ballerine tourne aussi (`:3010/:3011`) mais n'est pas retenu (README « rebuild, non supporté », orienté KYB, pas de SDK mobile).
Réserve connue (recherche live) : **le Sénégal n'est pas dans les 19 pays d'Idswyft** et la CNI sénégalaise n'est documentée nulle part → le support est à **tester**, pas à promettre.

## Partie B — Module KYC (Idswyft)

### B0. Spike avant tout code (porte de décision)
Avec la stack déjà lancée : créer une clé API dans le dashboard (OTP via `docker logs idswyft_api`), puis dérouler le flux en `curl`/script avec des photos **fournies par l'utilisateur** (CNI recto/verso, passeport, selfie) — je ne manipule jamais de vraie pièce moi-même. Mesurer : OCR des champs en français, lecture du verso (MRZ ?), liveness, face match. Écrire le résultat dans `docs/KYC.md`. **Si la CNI est mal lue** : le produit annonce « passeport » seulement et laisse `manual_review` (traité côté dashboard Idswyft) ; sinon CNI + passeport.

### B1. Backend (`backend-nest`, étendre le module existant `src/modules/kyc/` — placeholder `@Public()` à remplacer, déjà importé dans `app.module.ts`)
- **Config** (`config/configuration.ts` bloc `kyc`, `config/env.validation.ts`, `.env.example`, `.env.test.example`, `.env.prod.example`) : `IDSWYFT_BASE_URL` (défaut **`http://host.docker.internal:8000`** : le backend tourne dans le conteneur `dioteko-backend-nest`, `localhost` n'atteint pas `idswyft_api`), `IDSWYFT_API_KEY`, `IDSWYFT_WEBHOOK_SECRET` (optionnels, warning via `OPTIONAL_WARN_VARS`), `KYC_ENFORCEMENT=on|off` (défaut `on`, `off` autorisé hors production seulement). Ne jamais lire ni afficher le `.env` réel de l'utilisateur.
- **Client HTTP** `services/idswyft-http-client.service.ts` : copie du patron `BitnobHttpClientService` (axios, `timeout`, erreur typée `IdswyftApiError`, journal sans PII : code/statut seulement, `[CALL]/[RESULT]`).
- **Entité + migration** `kyc_verifications` (`1789000000000-CreateKycVerifications.ts`, réversible, relue par `@migration-reviewer`) : `user_id` FK RESTRICT + index, `provider` (`idswyft`), `provider_verification_id` unique, `status` (`pending|verified|failed|manual_review|rejected`), `document_type`, `issuing_country`, `attempts`, `verified_at`, `failure_reason`. **Jamais d'image, de numéro de pièce ni de données biométriques.** Petite table `kyc_webhook_events` (id d'événement unique, payload nettoyé, `processed`) pour l'idempotence sur `X-Idswyft-Webhook-Id` (patron `BitnobWebhookEvent`).
- **Upload** : ajouter `@types/multer` + `FileInterceptor` (déjà `@nestjs/platform-express`), limite 5 Mo, MIME `image/jpeg|png` seulement, flux transmis à Idswyft sans écriture disque ni base. Attention : `forbidNonWhitelisted` s'applique aux champs texte multipart.
- **Endpoints titulaire (JWT)** : `POST /api/kyc/sessions` (corps `{documentType}`, plafond de tentatives par jour géré chez nous, un seul dossier actif), `POST /api/kyc/sessions/:id/front|back|selfie`, `GET /api/kyc/status` (dernier dossier du titulaire ; si `pending`, relit le statut chez Idswyft = filet si le webhook est perdu). **Propriété** : une session d'un autre utilisateur répond 404.
- **Webhook** `POST /api/kyc/webhook/idswyft` : `@Public()` + garde de signature copiée de `BitnobWebhookSignatureGuard` (HMAC-SHA256, en-tête `X-Idswyft-Signature: sha256=<hex>`, `timingSafeEqual`, échec fermé en production si secret absent) sur le **rawBody**. Le webhook n'est qu'un **signal** : le statut est relu via `GET /api/v2/verify/:id/status` avant de passer `verified` (règle « la lecture fait foi » déjà utilisée pour Bitnob). À vérifier pendant le spike : Idswyft signe `JSON.stringify(payload)`, pas forcément les octets reçus.
- **Politique KYC par type (la brèche)** : dans `AdminCertificateTypeDefinition` (`admin-certificates.constants.ts`) un champ `kyc: 'required' | 'planned'`. Aujourd'hui : `residence` et `identity` = `required` (bloquant) ; `birth`, `marriage`, `death` = `planned` (cible obligatoire, **pas bloquant**, la demande passe). Une seule fonction `isKycEnforced(type)` décide : `required` → vrai ; `planned` → vrai seulement si le type figure dans `KYC_ENFORCED_TYPES` (liste séparée par virgules, ex. `birth,marriage,death`), ce qui permet d'activer la naissance, le mariage et le décès par configuration, puis plus tard en passant la valeur à `required`. `GET /admin-certificates/types` expose `kyc` pour que le mobile affiche « vérification requise » ou « bientôt obligatoire ». Dans `createRequest` (juste après la recherche du type, avant la validation des données) et `resubmitRequest` : `ForbiddenException` code `KYC_REQUIRED` si `isKycEnforced(type)` et `KYC_ENFORCEMENT=on` et pas de dossier `verified`. Tests : tableau complet type × politique × variable. Ne **pas** encore utiliser le nom vérifié comme nom du titulaire (D3 reste ouverte).
- **Préparer la suite pour la naissance (sans le coder maintenant)** : le KYC prouve **qui** demande, pas les données de l'acte. Pour un extrait de naissance, le nom du titulaire pourra être recoupé avec le nom lu sur la pièce, mais **père et mère ne figurent pas sur la CNI** : ils resteront saisis par le titulaire et à compléter (flux `needs_info` déjà en place) ou examinés par l'agent. Le plan note ce point dans `docs/KYC.md` et `ROADMAP_NEXT_STEPS.md` comme chantier suivant, sans stocker de nom vérifié pour l'instant.
- **Logs** `[START]/[ENTITY]/[CALL]/[RESULT]/[STATE]`, ids seulement.
- **Tests** : service (machine d'états, propriété, plafond, relecture), garde de signature (copier le spec Bitnob), gating dans `admin-certificates-*.spec.ts`, `configuration.spec.ts`/`env.validation.spec.ts`. Revues `@security-analyst` (webhook public + données personnelles) et `@migration-reviewer`.
